Публічний URL:

Налаштування:

Порт `10000` Render передає через змінну середовища `PORT`.

Spring Boot автоматично використовує цей порт.

## 4.2. Dockerfile

У корені репозиторію створено файл:

```text
wor-portal-app/Dockerfile
```

Його конфігурація:

```dockerfile
# ===============================
# STAGE 1: BUILD
# ===============================

FROM maven:3.9-eclipse-temurin-25 AS build

WORKDIR /app

COPY pom.xml .

COPY wor-portal-app-backend ./wor-portal-app-backend

RUN mvn clean package -pl wor-portal-app-backend -am -DskipTests


# ===============================
# STAGE 2: RUN
# ===============================

FROM eclipse-temurin:25-jre

WORKDIR /app

COPY --from=build /app/wor-portal-app-backend/target/*.jar app.jar

EXPOSE 8080

ENTRYPOINT ["java", "-jar", "app.jar"]
```

Використовується Multi-stage Docker Build.

На першому етапі Maven збирає Backend.

На другому етапі запускається готовий Spring Boot JAR.

Frontend у Docker-образ Backend не включається.

# 5. Backend — зміни application.properties

Файл:

```text
wor-portal-app-backend/src/main/resources/application.properties
```

Спочатку застосунок був налаштований тільки на локальну PostgreSQL:

```properties
server.port=8080

spring.datasource.url=jdbc:postgresql://localhost:5432/wor_portal_db
spring.datasource.username=postgres
spring.datasource.password=postgres_password
```

Ця конфігурація не підходила для Render, оскільки Backend не може використовувати `localhost` для підключення до PostgreSQL на іншому сервері.

Тому налаштування змінили.

### Нова конфігурація

```properties
# ===============================
# SERVER
# ===============================

server.port=${PORT:8080}
server.address=0.0.0.0

# ===============================
# LOGGING
# ===============================

logging.level.org.springframework.security=INFO

# ===============================
# DATABASE
# ===============================

spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/wor_portal_db}
spring.datasource.username=${DB_USERNAME:postgres}
spring.datasource.password=${DB_PASSWORD:postgres_password}
spring.datasource.driver-class-name=org.postgresql.Driver

# ===============================
# JPA / HIBERNATE
# ===============================

spring.jpa.hibernate.ddl-auto=validate
spring.jpa.show-sql=false
spring.jpa.properties.hibernate.format_sql=true
spring.jpa.open-in-view=false

# ===============================
# FLYWAY
# ===============================

spring.flyway.enabled=true
spring.flyway.baseline-on-migrate=true
```

### Що змінилося

**1. Динамічний порт**

```properties
server.port=${PORT:8080}
```

Локально використовується `8080`.

На Render використовується порт зі змінної `PORT`.

У логах підтверджено запуск на `10000`.

**2. Динамічне підключення до PostgreSQL**

```properties
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/wor_portal_db}
```

Локально застосунок використовує локальну PostgreSQL.

На Render — PostgreSQL із Neon.

**3. Логування Spring Security**

Було:

```properties
logging.level.org.springframework.security=TRACE
```

Стало:

```properties
logging.level.org.springframework.security=INFO
```

Це зменшує кількість службових повідомлень у production.

**4. SQL-логування**

Було:

```properties
spring.jpa.show-sql=true
```

Стало:

```properties
spring.jpa.show-sql=false
```

SQL-запити більше не виводяться постійно в консоль.

# 8. Виправлення Lombok для Java 25

Під час першого деплою Backend виникли помилки компіляції.

Приклади:

```text
cannot find symbol
method getUsername()
```

```text
cannot find symbol
method getId()
```

```text
cannot find symbol
method setGuild()
```

```text
cannot find symbol
method builder()
```

Причина полягала в тому, що Lombok не генерував необхідні методи під час Maven-збірки в Docker.

Для виправлення змінили:

```text
wor-portal-app-backend/pom.xml
```

У `<build>` додали явне налаштування Maven Compiler Plugin.

```xml
<build>
    <plugins>

        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>

            <configuration>
                <release>25</release>

                <annotationProcessorPaths>
                    <path>
                        <groupId>org.projectlombok</groupId>
                        <artifactId>lombok</artifactId>
                        <version>${lombok.version}</version>
                    </path>
                </annotationProcessorPaths>

            </configuration>
        </plugin>

        <plugin>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-maven-plugin</artifactId>

            <configuration>
                <excludes>
                    <exclude>
                        <groupId>org.projectlombok</groupId>
                        <artifactId>lombok</artifactId>
                    </exclude>
                </excludes>
            </configuration>

        </plugin>

    </plugins>
</build>
```

Це змусило Maven явно використовувати Lombok як Annotation Processor.

Після виправлення локальна збірка завершилася успішно.

Команда:

```bash
mvn clean package -pl wor-portal-app-backend -am -DskipTests
```

Результат:

```text
BUILD SUCCESS
```

Після `git push` Backend успішно задеплоївся на Render.

# 15. Помилка першого деплою Frontend

Під час збірки React на Render виникла помилка:

```text
UNRESOLVED_IMPORT
```

Render не міг знайти:

```text
./GvGCreatePresetPage
./GvGSearchPresetPage
./GvGBattlePage
```

Проблема була в регістрі літер.

### Реальні назви файлів

```text
GvgCreatePresetPage.jsx
GvgSearchPresetPage.jsx
GvgBattlePage.jsx
```

### Неправильні імпорти

У файлі:

```text
src/pages/gvg/GvgPage.jsx
```

Було:

```jsx
import GvGCreatePresetPage from "./GvGCreatePresetPage";
import GvGSearchPresetPage from "./GvGSearchPresetPage";
import GvGBattlePage from "./GvGBattlePage";
```

### Правильні імпорти

Потрібно використовувати:

```jsx
import GvGCreatePresetPage from "./GvgCreatePresetPage";
import GvGSearchPresetPage from "./GvgSearchPresetPage";
import GvGBattlePage from "./GvgBattlePage";
```

Причина:

Windows зазвичай не розрізняє регістр літер у назвах файлів.

Linux, який використовується Render, розрізняє.

Наприклад:

```text
GvGCreatePresetPage.jsx
```

і:

```text
GvgCreatePresetPage.jsx
```

для Linux — різні назви.

### Статус виправлення

Ми визначили причину помилки та надали точне виправлення.

**Але підтвердження успішного повторного деплою Frontend у переписці ще немає.**

Тому поточний статус Frontend — потребує перевірки після виправлення імпортів.

# 17. CORS — ще потрібно налаштувати

Оскільки Frontend і Backend розміщуються на різних доменах, браузер застосовує CORS.

Frontend:

```text
https://wor-portal-frontend.onrender.com
```

Backend:

```text
https://wor-portal-app.onrender.com
```

Для коректної роботи потрібно дозволити Frontend Origin у Spring Security.

Наприклад, Backend повинен приймати запити з:

```text
https://wor-portal-frontend.onrender.com
```

Це особливо важливо для:

```text
POST /api/auth/login
POST /api/auth/register
GET /api/users/me
```

Точні маршрути потрібно перевірити за контролерами Backend.

### Поточний статус CORS

Файл `SecurityConfig.java` ще не аналізували.

Тому невідомо, чи CORS уже правильно налаштований.

**Це один із наступних обов'язкових кроків.**

# 19. Що потрібно зробити далі

Наступні завдання в такому порядку:

1. Виправити імпорти в `GvgPage.jsx`, якщо це ще не зроблено.
2. Запустити локально `npm run build`.
3. Відправити виправлення на GitHub.
4. Дочекатися успішного деплою Render Static Site.
5. Відкрити Frontend через публічний URL.
6. Перевірити `SecurityConfig.java` і налаштувати CORS.
7. Перевірити реєстрацію користувача.
8. Перевірити авторизацію через JWT.
9. Перевірити запит `/api/users/me`.
10. Перевірити функціонал Guild, Heroes, GvG та Admin Panel.

Окремо варто перевірити, що пароль Neon було змінено після його випадкового розкриття.

Для production також бажано прибрати паролі за замовчуванням із `application.properties` і використовувати окрему конфігурацію для локальної розробки.

## 📌 Контекст для продовження роботи

Ми деплоїмо монорепозиторій WoR Portal App, який містить Spring Boot 4.1.1 Backend на Java 25 та React 19 + Vite 8 Frontend.

Backend уже успішно задеплоєний на Render через Docker, доступний за адресою `https://wor-portal-app.onrender.com` та підключений до Neon PostgreSQL через Environment Variables `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`.

Для Backend створено Dockerfile у корені репозиторію, змінено `application.properties` для підтримки локального та production-середовища, а також виправлено Maven Compiler Plugin для правильної роботи Lombok із Java 25.

Flyway успішно створив таблиці в Neon PostgreSQL. Spring Boot запустився на Render на порту 10000.

Frontend деплоїться окремо як Render Static Site з Root Directory `wor-portal-app-frontend/`, Build Command `npm ci && npm run build`, Publish Directory `dist` та Environment Variable `VITE_API_BASE_URL=https://wor-portal-app.onrender.com/api`.

Перший деплой Frontend завершився помилкою через неправильний регістр назв імпортованих GvG-компонентів у `GvgPage.jsx`. Правильні назви файлів: `GvgCreatePresetPage.jsx`, `GvgSearchPresetPage.jsx`, `GvgBattlePage.jsx`. Виправлення визначено, але повторний успішний деплой ще не підтверджений.

**Наступний етап: завершити деплой Frontend, перевірити CORS у Spring Security та протестувати авторизацію React → Spring Boot → Neon.**
