# ТЗ: Рефакторинг UserRoster.jsx

## 1. Мета

Є повністю робочий React-компонент `UserRoster`, який зараз містить понад 1000 рядків коду в одному файлі.

Завдання — **тільки логічно розділити код по файлах для покращення читабельності та підтримки**.

Функціональність, поведінка та зовнішній вигляд компонента не повинні змінитися.

Це НЕ переписування компонента і НЕ зміна архітектури застосунку.

---

## 2. Поточна структура проєкту

Проєкт має приблизно таку структуру:

```text
src/
├── api/
├── assets/
├── components/
└── pages/
    └── UserRoster/
```

`UserRoster` є сторінкою/модулем у:

```text
src/pages/UserRoster/
```

---

## 3. Цільова структура

У межах `src/pages/UserRoster/` поступово створити:

```text
src/
├── api/
├── assets/
├── components/
│
└── pages/
    └── UserRoster/
        ├── UserRoster.jsx
        │
        ├── components/
        │   ├── RosterFilters.jsx
        │   ├── HeroCard.jsx
        │   ├── FactionSection.jsx
        │   ├── LoadingState.jsx
        │   ├── ErrorState.jsx
        │   └── EmptyState.jsx
        │
        ├── constants/
        │   ├── rarityStyles.js
        │   └── factionOrder.js
        │
        └── utils/
            ├── factionUtils.js
            └── rosterUtils.js
```

Назви файлів можуть бути трохи скориговані під фактичний код, але загальний принцип залишається таким самим.

# 4. Головне правило

## НЕ ЗМІНЮВАТИ ПОВЕДІНКУ

Під час рефакторингу необхідно зберегти існуючу поведінку `UserRoster` один в один.

Не можна без окремої домовленості:

* змінювати API endpoints;
* змінювати HTTP methods;
* змінювати структуру API response;
* змінювати назви полів;
* змінювати алгоритм awakening;
* змінювати optimistic update;
* змінювати rollback після помилки;
* змінювати поведінку ЛКМ;
* змінювати поведінку ПКМ;
* змінювати фільтрацію;
* змінювати сортування;
* змінювати порядок фракцій;
* змінювати визначення Lord;
* змінювати визначення factionless;
* змінювати responsive layout;
* змінювати Tailwind-класи;
* змінювати зовнішній вигляд карток;
* додавати нові функції без необхідності;
* оптимізувати код без окремого прохання.

Ми робимо **структурний рефакторинг**, а не функціональний.

# 5. Поточний UserRoster

Поточний компонент вже повністю працює.

Він містить:

### State


### API


* підвищення awakening;

* rollback при помилці;
* пошук;
* фільтр за faction;
* фільтр за rarity;
* сортування;
* групування за faction;
* підтримка Lords;
* unknown factions;
* heroes без faction.

# 6. Принцип роботи

Рефакторинг виконувати **малими кроками**.

Не потрібно одразу переписувати весь файл.

Працювати за принципом:

```text
1 маленький шматок
↓
перенести
↓
додати import/export
↓
перевірити код
↓
запустити застосунок
↓
переконатися, що все працює
↓
перейти до наступного шматка
```

Після кожного кроку пояснювати:

1. який шматок переносимо;
2. з якого місця його вирізати;
3. у який файл вставити;
4. що саме експортувати;
5. який import додати;
6. що перевірити після цього.

---

# 7. Стиль роботи з користувачем

Користувач не є досвідченим React-розробником.

Тому пояснення мають бути максимально практичними.

Не давати абстрактних пояснень на кшталт:

> "винеси presentation layer у окремий модуль"

Замість цього:

> "Знайди у `UserRoster.jsx` ось цей блок. Виріж його повністю. Створи `components/HeroCard.jsx`. Встав туди цей код. Внизу додай `export default HeroCard`. Потім у `UserRoster.jsx` додай цей import."

Користувач має мати можливість буквально повторювати інструкції крок за кроком.

# 9. Наступні етапи

Рефакторинг бажано виконувати приблизно в такій послідовності.

## Етап 2 — constants

Винести:

```js
rarityStyles
```

у:

```text
constants/rarityStyles.js
```

Винести:

```js
factionOrder
```

у:

```text
constants/factionOrder.js
```

Логіку значень не змінювати.

---

## Етап 3 — faction utilities

Винести helper-функції:

```js
normalizeFaction
isLordFaction
getBaseFaction
heroBelongsToFaction
isHeroLordForFaction
factionToFileName
```

у:

```text
utils/factionUtils.js
```

Функції не переписувати без необхідності.

Їхня поведінка має залишитися такою самою.

---

## Етап 4 — roster utilities

Винести логіку:

* фільтрації;
* сортування;
* побудови faction groups;
* пошуку unknown factions;
* визначення factionless heroes.

у:

```text
utils/rosterUtils.js
```

Але тільки після того, як попередній етап перевірений.

---

## Етап 5 — HeroCard

Винести:

```js
renderHeroCard
```

у:

```text
components/HeroCard.jsx
```

Картка повинна залишитися візуально та функціонально ідентичною.

Вона повинна продовжити отримувати необхідні дані через props.

Не потрібно змінювати дизайн картки.

---

## Етап 6 — RosterFilters

Винести HTML та пов'язану з ним логіку фільтрів у:

```text
components/RosterFilters.jsx
```

Фільтри:

* search;
* faction;
* rarity;
* reset;
* показ кількості результатів.

---

## Етап 7 — FactionSection

Винести UI секції фракції:

```text
components/FactionSection.jsx
```

Вона повинна відповідати за:

* назву фракції;
* Lords;
* звичайних героїв;
* grids.

---

## Етап 8 — стани

За необхідності винести:

```text
LoadingState.jsx
ErrorState.jsx
EmptyState.jsx
```

Це прості UI-компоненти.

---

# 10. Що має залишитися в UserRoster.jsx

Після завершення рефакторингу `UserRoster.jsx` повинен бути головним компонентом-оркестратором.

Він має приблизно відповідати за:

* props `userId`;
* використання state;
* виклик API-логіки;
* підключення необхідних utility;
* збирання UI з компонентів.

Він НЕ повинен містити всю розмітку картки героя та всі helper-функції.

---

# 11. API логіку поки не змінювати

Поточні:

```js
useEffect
handleLeftClick
handleRightClick
```

спочатку залишаються як є.

Після того, як UI та utilities будуть рознесені, можна окремо розглянути винесення API/state логіки в hook.

Це не є обов'язковою частиною першого етапу.

Якщо винесення hook буде запропоновано, воно повинно виконуватися окремим етапом і без зміни поведінки.

---

# 12. Не робити передчасну оптимізацію

Не додавати без необхідності:

```js
useMemo
useCallback
memo
custom hooks
context
Redux
Zustand
React Query
нові бібліотеки
```

Мета — читабельність.

Не потрібно оптимізувати робочий код тільки тому, що він можна оптимізувати.

Якщо під час перенесення можна зробити два варіанти:

```text
A — красивіший / сучасніший
B — максимально близький до існуючого коду
```

Ми не покращуємо код.

# 15. Формат роботи асистента

Асистент повинен вести користувача буквально за руку.

На один крок — одна конкретна задача.

Приклад:

```text
КРОК 2. Виносимо rarityStyles

1. Відкрий UserRoster.jsx.
2. Знайди const rarityStyles = {...}.
3. Виріж весь цей блок.
4. Створи constants/rarityStyles.js.
5. Встав код.
6. Додай export.
7. У UserRoster.jsx додай import.
8. Запусти проєкт.
```

Після цього чекати підтвердження користувача.

Не видавати одразу 5 наступних кроків.
